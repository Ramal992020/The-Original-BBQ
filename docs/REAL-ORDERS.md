# التسجيل والطلبات الفعلية — إعداد التشغيل

## ما الذي يعمل الآن؟

- حساب **«صاحب المطعم»**، بدور `admin`، والبريد الافتراضي `aliielramal@gmail.com`.
- كلمة السر الأولية تأتي من إعداد خاص على السيرفر، وتتحول إلى **scrypt + salt**. لا تُنشر في Git أو الواجهة أو اللوجات.
- أي عميل ينشئ حسابًا يحصل على دور `customer` فقط، حتى لو حاول إرسال `role: admin` من المتصفح.
- الحسابات والجلسات والطلبات محفوظة على السيرفر، وليست تسجيلًا وهميًا في `localStorage`. المتصفح يحفظ فقط توكن الدخول، السلة، الثيم ومعرّف إعادة محاولة الطلب.
- الطلب مربوط بصاحبه، وأسعاره محسوبة من المنيو على السيرفر. الطلب والإشعار ورقم الطلب يُحفظون معًا **قبل** رد النجاح.
- يظهر الطلب لصاحب المطعم والمشرفين في `/#/admin?tab=orders`، مع إشعار داخل التطبيق. تغييرات الحالة تظهر للعميل في «طلباتي».
- إعادة إرسال نفس طلب التأكيد بعد انقطاع الاتصال لا تنشئ طلبًا ثانيًا؛ الواجهة ترسل `Idempotency-Key` محفوظًا حتى نجاح التأكيد. بعد النجاح يمكن إنشاء طلب جديد مطابق بصورة طبيعية.

**حدود مهمة:** ظهور الطلب في الإدارة لا يعني أن موظف المطعم قرأه أو وافق عليه. الحالة الأولى «طلب جديد»، ثم يؤكد الموظف الاستلام من لوحة الإدارة. لا توجد هنا متابعة GPS أو إرسال إشعار للهاتف بعد إغلاق التطبيق.

## ١. تشغيل محلي / سيرفر Node واحد

```bash
cp .env.example .env
# افتح .env في محرر آمن، واضبط ADMIN_PASSWORD بالكلمة المطلوبة.
npm start
```

البريد `ADMIN_EMAIL=aliielramal@gmail.com` جاهز في المثال. **لا تكتب كلمة السر في ملف عام أو README أو أمر يتسجل في التاريخ.**

ملف `.env` يُقرأ تلقائيًا، ومتغيرات الاستضافة تتغلب على قيمه. بديل كلمة السر النصية: متغير خاص `ADMIN_PASSWORD_HASH` بقيمة `salt:hash` من scrypt؛ لا تستخدم الاثنين معًا.

التخزين المحلي ملف واحد `server/data/database.json`، بصلاحيات `600`، يُكتب ذريًا بعد `fsync`. يعمل مع **عملية Node واحدة وقرص دائم**. على Render/VPS استخدم قرصًا دائمًا مثل:

```dotenv
STORAGE=file
BBQ_DATA_DIR=/var/data/bbq/data
BBQ_UPLOAD_DIR=/var/data/bbq/uploads
```

القرص المؤقت للاستضافة أو مجلد المشروع الذي يُستبدل عند النشر **ليس** تخزينًا دائمًا. لعدة نسخ من السيرفر استخدم Redis بدل الملف.

## ٢. تشغيل دائم على Vercel / عدة نسخ

يلزم إنشاء قاعدة **Upstash Redis** فعلية وربطها من **Environment Variables** في الاستضافة؛ الكود لا ينشئ حسابًا سحابيًا أو مفاتيح قاعدة بيانات نيابةً عنك.

| المتغير | القيمة |
|---|---|
| `STORAGE` | `redis` |
| `UPSTASH_REDIS_REST_URL` | رابط REST يبدأ بـ `https://` — ليس `redis://` |
| `UPSTASH_REDIS_REST_TOKEN` | التوكن الخاص من Upstash؛ لا ترسله في المحادثة |
| `ADMIN_EMAIL` | `aliielramal@gmail.com` |
| `ADMIN_PASSWORD` | كلمة السر الأولية المطلوبة، في الإعداد الخاص فقط |
| `APP_URL` | رابط التطبيق النهائي بـ HTTPS |
| `NODE_ENV` | `production` |
| `DEMO_LOGIN`, `SEED_DEMO`, `ALLOW_DEMO_PAYMENTS`, `ALLOW_CONSOLE_MAIL` | `0` |

استخدم قاعدة/بادئة `REDIS_PREFIX` منفصلة للمعاينة والاختبارات، ولا تجعل الاختبارات متصلة ببيانات عملائك.

بعد حفظ المتغيرات اعمل **Redeploy**. غياب Redis أو تعطل الحفظ ينتج `503`، ولا تتحول البيانات إلى `/tmp` أو حسابات تجريبية. الدالة تُحمّل البيانات المشتركة في كل طلب، بقفل موزع وحفظ ذري؛ وصول العميل لنسخة سيرفر مختلفة لا يخفي حسابه أو طلبه عن الإدارة.

على Vercel يتم تحديث الطلبات والإشعارات كل **٥ ثوانٍ أثناء فتح التطبيق**. على السيرفر العادي يستخدم التطبيق SSE لحظيًا، مع تحديث دوري احتياطي للحالات التي يفوت فيها حدث/تُستخدم عدة نسخ.

## ٣. التأكد من دورة الطلب

1. افتح `/api/health`: ينبغي `ok: true`، و`storage: redis` على Vercel. `503` يعني أن الإعداد أو قاعدة البيانات يحتاج إصلاحًا.
2. ادخل بالبريد السابق وكلمة السر التي ضبطتها؛ يفتح حساب صاحب المطعم ولوحة الإدارة.
3. في نافذة خاصة/جهاز آخر أنشئ حساب عميل، وأضف صنفًا، وأدخل رقم الهاتف والعنوان، ثم اختر **نقدًا عند التوصيل**.
4. بعد التأكيد يظهر رقم `BBQ-…` في «طلباتي» وطلبات الإدارة، ويظهر إشعار لصاحب المطعم.
5. غيّر الحالة من الإدارة إلى «تم استلام الطلب» ثم «جاري التجهيز»؛ تحقق من تحديث شاشة العميل.
6. أعد تشغيل السيرفر/انشر نسخة أخرى؛ سجّل الدخول وتأكد أن الحساب والطلب والإشعار ما زالوا موجودين.

لا تظهر الحسابات التجريبية افتراضيًا. عند ترقية بيانات قديمة تُعطَّل فقط حسابات التجربة المعروفة التي **ما زالت تستخدم كلمات سرها الافتراضية**، وتبقى طلباتها محفوظة. حساب غُيّرت كلمة سره لا يُحذف. يُجهَّز حساب المالك حتى لو كان عندك عملاء بالفعل، ولا تُعاد كلمة سره القديمة بعد أن يغيّرها من **حسابي → تغيير كلمة السر**.

## ٤. الخدمات الاختيارية ليست شرطًا لاستلام الطلب داخل التطبيق

- **الدفع:** الطلبات النقدية فعلية؛ الدفع الأونلاين لا يظهر للعميل حتى إعداد Stripe/Paymob بمفاتيح وWebhook. محاكاة الدفع مقفولة في الإنتاج.
- **واتساب:** غير مفعل افتراضيًا. للإرسال التلقائي الحقيقي اضبط مزودًا ورقمًا من لوحة الإدارة. `console` و`link` ليسا إرسالًا تلقائيًا فعليًا.
- **استعادة كلمة السر بالبريد:** تحتاج `RESEND_API_KEY` و`MAIL_FROM` من نطاق موثَّق. بدونها يوضح التطبيق أن الخدمة غير مفعّلة، ولا يدّعي أنه أرسل رسالة. تغيير كلمة السر من داخل الحساب يعمل دون خدمة بريد.
- غيّر بيانات المطعم الافتراضية (الهاتف، العنوان، رسوم التوصيل، المواعيد)، وراجع المنيو قبل قبول طلبات الجمهور.

## الاختبارات

```bash
npm run test:all
```

يشمل التسجيل والصلاحيات، حفظ البيانات بعد إعادة التشغيل، نسختين دافئتين من السيرفر تشتركان في Redis، تسجيلات/طلبات متزامنة، إعادة المحاولة، تعطل القرص/Redis، فساد البيانات وعدم فقدها، حماية المالك وتغيير كلمة السر، والواجهة.

اختبارات Redis تستخدم محاكيًا محليًا للتأكد من السلوك؛ **ليست دليلًا على اتصال بقاعدة Upstash خارجية**. جميع الاختبارات تعمل على بيانات معزولة ولا تعدّل بيانات المطعم الفعلية.
